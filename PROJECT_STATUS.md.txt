## Known Issues

* Live Redis round-trip/expiry/removal is implemented but skipped without REDIS_TEST_CONNECTION_STRING. SQL post-commit invalidation is reviewed and its success/failure control flow is tested using explicit EF InMemory; actual SQL transaction/runtime verification remains deferred.
* Cache invalidation is best effort after SQL commit. Redis outage, process termination between commit/invalidation or direct SQL edits can leave cached display/management DTOs stale until absolute TTL (default two minutes, configured maximum ten). Financial calculations and critical eligibility reads bypass these caches.
* Shipping SQL persistence, native rowversion conflicts, concurrent creation/transition, uniqueness and flushed audit rollback remain unverified against live SQL Server. Five implemented Shipping SQL tests are explicitly skipped.
* True verified Payment -> paid Order -> Shipment E2E is blocked/skipped by missing Phase 8. Shipment creation requires a paid/Processing physical Order; tests use explicit trusted Order domain fixtures, not a fake Payment implementation. Payment was not added or bypassed.
* Legacy/unselected Orders retain original totals and ShippingCost=0, but lack the full captured shipping selection/address required by new Shipment creation. A future authorized fulfillment/backfill policy is needed; no historical purchase/address/cost data was fabricated. Physical checkout must provide Shipping to use the new fulfillment flow.
* Phase 12 supports one shipment per Order and flat configured method cost. Split fulfillment, external carrier pricing, taxes, address books and automatic Order lifecycle synchronization are deferred. Shipping cancellation is logistics-only and performs no refund/restocking.
* Phase 8 Payment entities/state/producer and authoritative IRefundPaymentEvidence adapter remain absent. No Payment functionality was duplicated. Refund scheduling does not dispatch without an adapter; completion cannot credit without matching evidence. True Payment-to-Inventory-to-delayed-Refund-to-Wallet end-to-end coverage is explicitly blocked/skipped.
* The future Payment adapter must verify successful server-side payment and full-refund eligibility, including competing refund/reversal coordination. This phase supports one full Inventory refund per PaymentId; partial/split payment and payment-state orchestration remain outside its scope. Order snapshots establish candidate owner/value, not proof of successful payment.
* Five Refund SQL tests remain unverified at runtime: local Refund/Outbox/Inbox rollback, concurrent requests/scheduling, uniqueness, duplicate consumption and Wallet-commit/refund-rollback recovery. The existing skipped RabbitMQ adapter test now includes duplicate refunds.due.v1 delivery. No live database/broker was accessed.
* Refund and Wallet deliberately use separate local transactions with stable-key recovery. Terminal Inbox/Outbox failures can leave Processing refunds for reconciliation. Failed or uncertain Wallet outcomes must be reconciled using the original PaymentId/credit key and Wallet ledger before controlled recovery; no automated destructive reset or arbitrary refund API was added.
* Messaging SQL claim/lease behavior, transaction rollback, application locks, concurrent Inbox processing and savepoints remain unverified against live SQL Server. Seven Messaging SQL tests and five affected Order SQL tests are implemented and skipped. Shared transaction contexts require the same physical database and MultipleActiveResultSets disabled.
* One RabbitMQ adapter/topology/confirmation test is implemented and skipped without a broker. Deployment must supply matching routes, queues, credentials and trusted-producer access controls; workers default to disabled.
* True Payment -> Outbox -> RabbitMQ -> Inventory end-to-end verification is explicitly blocked/skipped because Phase 8 is absent. Phase 10 creates only the versioned inbound contract and Inventory consumer; Payment production, verification, allocation selection and Order paid-state orchestration remain pending Phase 8. No Payment module or fake Payment implementation was created.
* Messaging guarantees at-least-once delivery with durable consumer deduplication, not exactly-once broker transport. Terminal failures retain source payload and safe diagnostics; controlled recovery/retention is documented and no automated destructive purge was added. Inventory shortage emits the existing failure event consumed by the Phase 11 Refund foundation.
* Wallet SQL transaction rollback, native conditional update behavior, application locking, concurrent debit/replay handling, relational constraints and immutable-ledger trigger remain unverified at runtime without SQL Server. Six implemented Wallet SQL tests are explicitly skipped, including the mandatory 1,000,000 balance/two 700,000 debits scenario.
* Payment is absent from the repository and Phase 8 is not complete. Phase 11 reuses Wallet's trusted credit contract for guarded refund processing; no payment-from-wallet workflow or Payment implementation was added.
* Wallet owns its local transaction. Future cross-module financial workflows must define authorization, stable operation/reference IDs and their consistency protocol. Phase 10 adds shared messaging infrastructure but does not integrate Wallet financial workflows or introduce distributed transactions.
* Order SQL runtime persistence, shared Order/Cart transaction rollback, concurrent idempotency, uniqueness and rowversion remain unverified without SQL Server. Five implemented Order SQL tests are explicitly skipped.
* Order/Cart atomic enlistment assumes the current shared physical SQL Server database and scoped contexts. Separate-service extraction will need a durable consumption/reconciliation protocol; it was not implemented now.
* Checkout checks physical availability across active warehouses without allocating a fulfilment warehouse, reserving or deducting stock. It does not guarantee availability when payment is verified later.
* Unpaid checkout checks discount eligibility but does not consume usage. Verified-payment purchase/redemption accounting remains deferred; Phase 12 adds Shipping selection/cost/fulfillment without implementing Payment or accepted-payment discount accounting.
* Pricing/Discount SQL runtime persistence, schedule locking, transaction rollback, rowversion and Cart/Inventory isolation remain unverified without SQL Server. Five implemented Phase 6 SQL tests are explicitly skipped.
* Discount previews never consume usage. Usage limits/counts support eligibility, but accepted-order redemption and atomic usage accounting belong to a future checkout/order workflow.
* Pricing previews are informational snapshots across module-owned contexts, not binding checkout totals. A later checkout must recalculate and define acceptance boundaries.
* Cart SQL runtime persistence, unique constraints, transactional rollback, rowversion concurrency and same-database Inventory isolation remain pending Docker SQL Server. Five implemented SQL-backed Cart tests are skipped while SQL Server is unavailable.
* Inventory runtime SQL locking, affected-row behavior, relational constraints, transaction rollback and concurrent retry behavior remain unverified without SQL Server. Eight implemented SQL integration tests, including the last-unit concurrency test, are skipped pending Docker SQL Server.
* Inventory quantities are whole SKU units. Fractional bulk measurements are outside the Phase 4 model.
* Catalog SQL query execution, relational constraints, transaction rollback, rowversion concurrency and hierarchy application locks remain unverified against a live SQL Server. These database-dependent checks were skipped/deferred to Docker SQL Server.
* SQL-backed persistence, constraints and concurrent refresh rotation remain unverified at runtime. The user explicitly deferred these integration tests to Docker SQL Server; this does not block Phase 2 completion under the revised scope.
* SQL Server/LocalDB is not available on this machine. No SQL Server or LocalDB installation/use or persistent database modification is authorized for current validation.

## Important Decisions

### Identity

* Registration requires only FirstName, LastName, Email and Password; PhoneNumber is optional. Address, national ID, birth date and gender are not registration requirements.
* Normalized email is unique; optional phone uses international +countrycode format and a filtered unique index.
* Public registration assigns Customer only and creates an active account. OTP/contact verification is deferred.
* PasswordHasher uses 600,000 iterations with rehash-on-login support. Passwords are 12–128 characters with upper/lowercase, digit and symbol rules.
* JWT signing keys come only from secure configuration/environment; there is no checked-in key or development fallback.
* Access tokens default to 10 minutes; refresh sessions have an absolute 30-day lifetime.
* Refresh secrets are 256-bit random values; only SHA-256 hashes are persisted. Consumed-token replay revokes the whole session.
* Authentication/rotation/logout/status operations serialize relevant user changes with SQL row locks and commit audit with business state.
* Each authenticated request checks persisted active user/session state and reloads role/permission assignments for immediate revocation.
* Role assignments invalidate existing access tokens; permission changes are enforced from current persisted assignments.
* Initial administrator creation is an explicit one-time command using secure configuration, guarded by a SQL application lock. No bootstrap endpoint exists.
* Shared ApiResponse moved to BuildingBlocks Abstractions for module reuse. Foundation's existing exception pipeline accepts safe application errors; the Foundation was not redesigned.
* No OTP/SMS, RabbitMQ, Redis or Phase 3+ business functionality was added.
* Per the user's revised instructions, Phase 2 completion requires the affected build and database-free tests. Database-dependent tests are skipped and will run later using Docker SQL Server.
* SQL Server EF Core Code First and migrations remain configured. There is no development LocalDB connection fallback.

### Catalog

* Product remains generic; variant dimensions are reusable attribute/value records rather than hardcoded clothing fields.
* Variant IDs are stable GUIDs. SKUs are normalized uppercase and globally unique within Catalog; sorted attribute combinations are unique within each product.
* A simple product has one base SKU. Variant attribute dimensions cannot change after variants exist, and options used by variants cannot be removed.
* Specifications and bounded metadata are independent of variant selections. Images use ordered HTTPS URLs; upload/storage infrastructure is deferred.
* Products start Draft, and publishing requires an active variant. Public reads hide inactive product references and inactive variant attributes/values.
* PUT product replaces its details/options and preserves variants. Weight is in grams and dimensions in millimeters; digital products cannot carry physical measurements.
* Catalog owns its schema, context and migration history. Commands use transactions and root rowversion concurrency; category hierarchy mutations additionally use a SQL application lock.
* Existing Identity authorization is reused through catalog.manage. The permission is added with an incremental seed migration, without redesigning Identity.
* SQL integration verification is deferred to Docker SQL Server under the user's current validation scope.

### Inventory

* Inventory owns quantities, warehouses and movements. Catalog variant identity/kind/activation is supplied by a small explicit contract; no Catalog quantity fields or cross-module table access were added.
* Stock is unique per warehouse/variant. Quantities are nonnegative whole units; inactive stock/warehouses expose zero available quantity.
* All quantity changes use a conditional SQL UPDATE with OUTPUT, checked for exactly one changed row, inside the same transaction as movement and receipt/adjustment history.
* Movements retain signed delta, before/after quantities, operation/business references, UTC timestamp, actor, reason and correlation. History is append-only through EF and protected by restrictive foreign keys.
* Required operation IDs serialize duplicate retries with a transaction-owned application lock and unique movement index. Exact retries return the original result; changed payload/actor returns 409. A narrow creation lock protects the first stock row.
* Existing Identity permissions are reused: inventory.view, inventory.receive, inventory.adjust and inventory.deduct. API actors come from authenticated claims.
* Deduction is an internal IInventoryDeduction contract with no HTTP endpoint. A later verified-payment workflow must explicitly invoke it; that workflow was not implemented.
* Cart does not reserve stock. No reservations or refund logic were added.
* Phase 4 completion uses successful available validation as requested; database integration/concurrency tests remain deferred to Docker SQL Server.

### Cart

* Cart quantity is requested quantity, never reserved stock. Cart has no Inventory/Pricing dependency and performs no inventory reads/writes/locks or movement creation.
* One active cart per authenticated user and one item per cart/variant are enforced with unique indexes. User authority comes from the server's sub claim; item mutations are scoped to that owner's active cart.
* GET remains read-only and returns an empty DTO when no persisted cart exists. First Add creates the cart; duplicate Add increments quantity; PUT replaces quantity; remove/clear do not validate inactive variants so users can clean up their cart.
* Limits are 999 whole units per item and 100 distinct items. Catalog's existing variant contract provides purchasability validation for add/update; both physical and digital variants are allowed.
* Item changes bump the root revision, causing a rowversion concurrency check inside the command transaction. Overlapping writes or uniqueness races return 409; no additional locks or Serializable isolation were introduced.
* Cart responses contain IDs, quantities and UTC timestamps. Prices, discounts, coupons and checkout totals are neither stored nor calculated.
* SQL-backed Cart validation is deferred to Docker SQL Server under the user's requested available-validation scope.

### Pricing and Discount

* Pricing owns variant/currency price schedules and immutable audit snapshots. Compare price is informational and cannot be lower than base price.
* Active periods use inclusive start/exclusive end. Narrow transaction-owned SQL application locks precede mutable price loading and overlap checks; rowversion adds stale-write protection.
* Supported currencies: IRR uses whole units; USD/EUR/GBP/AED/TRY use two decimal places. Inputs must respect currency precision; unit savings round midpoint away from zero before quantity multiplication.
* Exactly one discount per line: highest priority, greatest rounded saving, then smallest GUID. Fixed savings are per unit and clamp to base price. Discounts do not stack.
* A rule targets one variant, product, exact category or all products. Codes normalize uppercase. MinimumOrderAmount uses the server-calculated base subtotal across preview lines; category descendants and currency conversion are deferred.
* UsedCount/UsageLimit eligibility is persisted but previews never redeem/consume usage. Atomic accepted-order redemption is deferred.
* Catalog's reference contract supplies product/category IDs and a batched SQL projection. Catalog still owns no authoritative prices; Cart still persists quantities only.
* Cart pricing is hosted by Pricing Presentation through Cart.Contracts, uses authenticated ownership, reloads current prices and does not read/write/reserve Inventory.
* Existing Identity permission handling is extended with pricing.manage and discount.manage through an incremental seed migration. Foundation/Identity infrastructure was reused without redesign.
* Pricing quotes are informational previews. Checkout must recalculate in a later phase. SQL runtime verification remains deferred.

### Order and Checkout

* Checkout loads the authenticated owner's active Cart/revision, validates Catalog variants, recalculates through Pricing/Discount, checks advisory Inventory availability and persists historical snapshots in AwaitingPayment.
* Pending -> AwaitingPayment/Cancelled/Failed; AwaitingPayment -> Paid/Cancelled/Failed; Paid -> Processing; Processing -> Shipped; Shipped -> Completed. Completed/Cancelled/Failed are terminal.
* Customers cancel only their own Pending/AwaitingPayment orders. Administrative state changes follow the graph and cannot set Paid; that edge is reserved for future trusted payment verification.
* Order/items/address/currency/totals are historical snapshots. EF protects purchase data and audit from mutation; root status changes use revision/rowversion and append actor/time/correlation audit.
* Existing money precision and rounding apply, including the shared 1,000,000,000,000 bound on line/order totals. Payable amount includes discounted merchandise plus the optional Phase 12 shipping quote; taxes and currency conversion remain deferred.
* Optional legacy Checkout address data remains unchanged; Phase 12 adds a full immutable shipping method/cost/address snapshot without changing Identity registration. Physical availability remains advisory across active warehouses; digital products require no warehouse stock or shipping selection.
* IdempotencyKey is a required GUID, scoped to the server-authenticated owner and persisted with a normalized structured request fingerprint. Replays resolve before Cart/current product/price validation, return the same Order and never clear a new Cart.
* A narrow per-user SQL checkout application lock and unique user/key + Cart/revision indexes prevent duplicate consumption. Cart revision/rowversion protects concurrent edits.
* Cart implements a small checkout snapshot/conditional-clear contract. A generic infrastructure-only SQL transaction participant shares one connection/transaction between module-owned Cart and Order contexts. Validation failures or save failures roll back both; no ambient/distributed transaction was introduced.
* Catalog variant references now include product name for snapshots; Inventory exposes a batched read-only availability contract. Existing module internals and migrations were preserved.
* Checkout/cancellation never deduct or reserve stock, create movements, call payment services or create refunds. Unpaid orders do not consume discount usage; payment/redemption/final stock deduction remain later work.
* SQL runtime verification is deferred; Phase 7 completion uses the successful available validation requested by the user.

### Payment

Payment verification is server-side.

Payment operations must be idempotent.

### Wallet

* Wallet owns wallet schema/context/history and has one primary wallet per user. First successful credit creates it; reads create nothing and return 404 beforehand. First credit fixes the wallet currency.
* Signed ledger convention: credit positive, debit negative, Posted for successful entries only. Failed debits post nothing. Before/after balances, signed amount, references, actor, timestamp and correlation retain immutable financial history.
* Money reuses Pricing.Contracts currency/precision rules and the 1,000,000,000,000 bound. SQL monetary fields use decimal(18,4); input precision is validated, balances never negative and currency conversion is deferred.
* Each posting uses a transaction-owned per-user SQL application lock, a conditional SQL balance UPDATE with actual OUTPUT before/after values, and one matching ledger insertion in the same transaction. Failure rolls back creation/balance/ledger together.
* Idempotency is persisted with a unique wallet/key and normalized structured fingerprint including canonical decimal amount, actor, direction and reference. Exact replays return the original result; changed payload/actor fails 409. Wallet/type/reference uniqueness additionally prevents reposting a business reference with a new key.
* EF posting guards protect financial consistency and immutable history; SQL trigger rejects historical ledger UPDATE/DELETE and restrictive relationships prevent removing referenced wallets. InitialWallet Down refuses destructive financial-history removal.
* wallet.credit reuses Identity permission policies and an incremental Administrator grant. Administrative target users are validated through the existing Identity query contract; actor/owner authority comes from authenticated claims.
* Credit/debit remain trusted application contracts. No customer charging/debit endpoint or payment-from-wallet is implemented; Phase 11 now reuses credit for guarded delayed refunds. Phase 8 remains incomplete.
* Wallet commits its own module-local transaction. Cross-module financial orchestration, outbox/messaging and reconciliation belong to later explicitly requested work. Redis is not used for balance or idempotency.
* Phase 9 completion uses successful available validation as requested. Six SQL integration tests remain deferred; actual SQL concurrency/transaction/constraint behavior has not been verified against a live server.

### Refund

If payment succeeds but inventory is unavailable, refund processing is asynchronous and delayed.

Do not block a request/thread for one hour.

* Refund coordination has a separate owned schema/module because durable scheduling, retry and cross-module recovery are distinct from Wallet balance/ledger ownership. Module internals remain isolated; communication uses Order, Inventory and Wallet contracts.
* Existing inventory.unavailable.v1 requests one full refund per PaymentId through shared Inbox/Outbox. An immutable Order snapshot supplies owner and candidate amount; required authoritative Payment evidence must match before credit.
* DueAtUtc persists the configurable delay (default 60 minutes). Per-payment transaction application locks, reload and unique keys protect scheduling/request concurrency. Processing represents an atomically scheduled durable due event.
* Wallet retains its original independent balance/ledger transaction. Stable credit keys/reference/fingerprints handle the commit gap before Refund/Inbox/Outbox completion without double credit. No distributed transaction or direct Wallet table mutation is introduced.
* Durable attempt counts/backoff/failure codes retain failures. Safe terminal events, correlation and ledger references support reconciliation; no arbitrary refund API or automated financial-history deletion exists.
* Scheduler/Completion require a future Phase 8 payment-evidence adapter; no default fake verification is provided. Production requests remain Pending without it. Refund foundation completion does not imply live Payment integration or SQL/broker runtime validation.

### Messaging

Important integration events use Transactional Outbox before RabbitMQ publication.

* Messaging owns persistence independently of Foundation and business contexts. Local SQL participants share a connection/transaction; no distributed transaction is used.
* Checkout persists orders.created.v1 atomically with Order and Cart changes. Outbox writing requires an enlisted transaction and preserves immutable IDs/content across retries.
* RabbitMQ.Client 7.2.2 publication awaits publisher confirmations with mandatory routing and persistent messages. Durable configurable topology and reconnecting workers are disabled unless explicitly configured.
* SQL leases fence concurrent publishers; bounded exponential retry dates/counts and terminal failures survive restarts. Confirmed publication can be replayed after bookkeeping failure, so consumers must remain idempotent.
* Inbox is unique by MessageId/ConsumerName, checks immutable fingerprints and commits with Inventory effects. Broker acknowledgement follows durable commit; rejected business effects roll back before failure Outbox/Inbox persistence.
* Payment success consumes explicitly allocated warehouse/variant lines through existing Inventory deduction. Stable payment-derived operation IDs add protection against a producer replay with a new event ID. Digital-only success may contain no stock lines.
* Inventory shortage records inventory.unavailable.v1 without performing refunds. Future Phase 8 must produce verified, authorized success events and define allocation and paid-order orchestration; Phase 11 remains separate.
* Correlation propagates into existing audit/logging infrastructure. Payloads, tokens, credentials and raw exception messages are not logged. Broker secrets and deployment topology come from external configuration.

### Shipping

* Shipping owns its methods, calculator, shipment state, tracking and audit. It communicates through a small Order read contract and has no financial-module or Inventory mutation dependency.
* Optional checkout Shipping selection uses server method/currency/address validation and preserves the quote in Order. PayableAmount adds ShippingCost; existing no-selection fingerprints/totals remain unchanged. Shipment copies original quote details rather than current method prices or profile addresses.
* One shipment per paid physical Order is enforced through application validation and a unique OrderId index. Existing unselected Orders are not silently backfilled/repriced. Multi-package fulfillment remains later work.
* Controlled state transitions use ExpectedRevision and SQL rowversion. Tracking/carrier become immutable at dispatch; configured tracking requirements support generic collection/custom methods without hardcoded type branches.
* Customer shipment reads validate Order ownership; management/view/method policies require explicit Identity permissions, never role-name bypass. Shipping audit commits with state and structured logs omit personal/payment data.
* No automatic Order status mutation or unnecessary RabbitMQ event/consumer is introduced. SQL concurrency/runtime and true verified-payment fulfillment remain deferred; Phase 8 is not implemented here.
