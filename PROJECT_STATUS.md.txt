## Important Decisions

### Identity

* Registration requires only FirstName, LastName, Email and Password; PhoneNumber is optional. Address, national ID, birth date and gender are not registration requirements.
* Normalized email is unique; optional phone uses international +countrycode format and a filtered unique index.
* Public registration assigns Customer only and creates an active account. OTP/contact verification is deferred.
* PasswordHasher uses 600,000 iterations with rehash-on-login support. Passwords are 12–128 characters with upper/lowercase, digit and symbol rules.
* JWT signing keys come only from secure configuration/environment; there is no checked-in key or development fallback.
* Access tokens default to 10 minutes; refresh sessions have an absolute 30-day lifetime.
* Refresh secrets are 256-bit random values; only SHA-256 hashes are persisted. Consumed-token replay revokes the whole session.
* Authentication/rotation/logout/status operations serialize relevant user changes with SQL row locks and commit audit with business state.
* Each authenticated request checks persisted active user/session state and reloads role/permission assignments for immediate revocation.
* Role assignments invalidate existing access tokens; permission changes are enforced from current persisted assignments.
* Initial administrator creation is an explicit one-time command using secure configuration, guarded by a SQL application lock. No bootstrap endpoint exists.
* Shared ApiResponse moved to BuildingBlocks Abstractions for module reuse. Foundation's existing exception pipeline accepts safe application errors; the Foundation was not redesigned.
* No OTP/SMS, RabbitMQ, Redis or Phase 3+ business functionality was added.
* Per the user's revised instructions, Phase 2 completion requires the affected build and database-free tests. Database-dependent tests are skipped and will run later using Docker SQL Server.
* SQL Server EF Core Code First and migrations remain configured. There is no development LocalDB connection fallback.

### Catalog

* Product remains generic; variant dimensions are reusable attribute/value records rather than hardcoded clothing fields.
* Variant IDs are stable GUIDs. SKUs are normalized uppercase and globally unique within Catalog; sorted attribute combinations are unique within each product.
* A simple product has one base SKU. Variant attribute dimensions cannot change after variants exist, and options used by variants cannot be removed.
* Specifications and bounded metadata are independent of variant selections. Images use ordered HTTPS URLs; upload/storage infrastructure is deferred.
* Products start Draft, and publishing requires an active variant. Public reads hide inactive product references and inactive variant attributes/values.
* PUT product replaces its details/options and preserves variants. Weight is in grams and dimensions in millimeters; digital products cannot carry physical measurements.
* Catalog owns its schema, context and migration history. Commands use transactions and root rowversion concurrency; category hierarchy mutations additionally use a SQL application lock.
* Existing Identity authorization is reused through catalog.manage. The permission is added with an incremental seed migration, without redesigning Identity.
* SQL integration verification is deferred to Docker SQL Server under the user's current validation scope.

### Inventory

* Inventory owns quantities, warehouses and movements. Catalog variant identity/kind/activation is supplied by a small explicit contract; no Catalog quantity fields or cross-module table access were added.
* Stock is unique per warehouse/variant. Quantities are nonnegative whole units; inactive stock/warehouses expose zero available quantity.
* All quantity changes use a conditional SQL UPDATE with OUTPUT, checked for exactly one changed row, inside the same transaction as movement and receipt/adjustment history.
* Movements retain signed delta, before/after quantities, operation/business references, UTC timestamp, actor, reason and correlation. History is append-only through EF and protected by restrictive foreign keys.
* Required operation IDs serialize duplicate retries with a transaction-owned application lock and unique movement index. Exact retries return the original result; changed payload/actor returns 409. A narrow creation lock protects the first stock row.
* Existing Identity permissions are reused: inventory.view, inventory.receive, inventory.adjust and inventory.deduct. API actors come from authenticated claims.
* Deduction is an internal IInventoryDeduction contract with no HTTP endpoint. A later verified-payment workflow must explicitly invoke it; that workflow was not implemented.
* Cart does not reserve stock. No reservations or refund logic were added.
* Phase 4 completion uses successful available validation as requested; database integration/concurrency tests remain deferred to Docker SQL Server.

### Cart

* Cart quantity is requested quantity, never reserved stock. Cart has no Inventory/Pricing dependency and performs no inventory reads/writes/locks or movement creation.
* One active cart per authenticated user and one item per cart/variant are enforced with unique indexes. User authority comes from the server's sub claim; item mutations are scoped to that owner's active cart.
* GET remains read-only and returns an empty DTO when no persisted cart exists. First Add creates the cart; duplicate Add increments quantity; PUT replaces quantity; remove/clear do not validate inactive variants so users can clean up their cart.
* Limits are 999 whole units per item and 100 distinct items. Catalog's existing variant contract provides purchasability validation for add/update; both physical and digital variants are allowed.
* Item changes bump the root revision, causing a rowversion concurrency check inside the command transaction. Overlapping writes or uniqueness races return 409; no additional locks or Serializable isolation were introduced.
* Cart responses contain IDs, quantities and UTC timestamps. Prices, discounts, coupons and checkout totals are neither stored nor calculated.
* SQL-backed Cart validation is deferred to Docker SQL Server under the user's requested available-validation scope.

### Pricing and Discount

* Pricing owns variant/currency price schedules and immutable audit snapshots. Compare price is informational and cannot be lower than base price.
* Active periods use inclusive start/exclusive end. Narrow transaction-owned SQL application locks precede mutable price loading and overlap checks; rowversion adds stale-write protection.
* Supported currencies: IRR uses whole units; USD/EUR/GBP/AED/TRY use two decimal places. Inputs must respect currency precision; unit savings round midpoint away from zero before quantity multiplication.
* Exactly one discount per line: highest priority, greatest rounded saving, then smallest GUID. Fixed savings are per unit and clamp to base price. Discounts do not stack.
* A rule targets one variant, product, exact category or all products. Codes normalize uppercase. MinimumOrderAmount uses the server-calculated base subtotal across preview lines; category descendants and currency conversion are deferred.
* UsedCount/UsageLimit eligibility is persisted but previews never redeem/consume usage. Atomic accepted-order redemption is deferred.
* Catalog's reference contract supplies product/category IDs and a batched SQL projection. Catalog still owns no authoritative prices; Cart still persists quantities only.
* Cart pricing is hosted by Pricing Presentation through Cart.Contracts, uses authenticated ownership, reloads current prices and does not read/write/reserve Inventory.
* Existing Identity permission handling is extended with pricing.manage and discount.manage through an incremental seed migration. Foundation/Identity infrastructure was reused without redesign.
* Pricing quotes are informational previews. Checkout must recalculate in a later phase. SQL runtime verification remains deferred.

### Order and Checkout

* Checkout loads the authenticated owner's active Cart/revision, validates Catalog variants, recalculates through Pricing/Discount, checks advisory Inventory availability and persists historical snapshots in AwaitingPayment.
* Pending -> AwaitingPayment/Cancelled/Failed; AwaitingPayment -> Paid/Cancelled/Failed; Paid -> Processing; Processing -> Shipped; Shipped -> Completed. Completed/Cancelled/Failed are terminal.
* Customers cancel only their own Pending/AwaitingPayment orders. Administrative state changes follow the graph and cannot set Paid; that edge is reserved for future trusted payment verification.
* Order/items/address/currency/totals are historical snapshots. EF protects purchase data and audit from mutation; root status changes use revision/rowversion and append actor/time/correlation audit.
* Existing money precision and rounding apply, including the shared 1,000,000,000,000 bound on line/order totals. Payable amount is discounted merchandise lines only; tax/shipping charges and currency conversion are deferred.
* Optional Checkout address data is snapshotted without adding profile or Shipping infrastructure. Physical availability is aggregated across active stocks/warehouses; digital products require no warehouse stock.
* IdempotencyKey is a required GUID, scoped to the server-authenticated owner and persisted with a normalized structured request fingerprint. Replays resolve before Cart/current product/price validation, return the same Order and never clear a new Cart.
* A narrow per-user SQL checkout application lock and unique user/key + Cart/revision indexes prevent duplicate consumption. Cart revision/rowversion protects concurrent edits.
* Cart implements a small checkout snapshot/conditional-clear contract. A generic infrastructure-only SQL transaction participant shares one connection/transaction between module-owned Cart and Order contexts. Validation failures or save failures roll back both; no ambient/distributed transaction was introduced.
* Catalog variant references now include product name for snapshots; Inventory exposes a batched read-only availability contract. Existing module internals and migrations were preserved.
* Checkout/cancellation never deduct or reserve stock, create movements, call payment services or create refunds. Unpaid orders do not consume discount usage; payment/redemption/final stock deduction remain later work.
* SQL runtime verification is deferred; Phase 7 completion uses the successful available validation requested by the user.

### Payment

Payment verification is server-side.

Payment operations must be idempotent.

### Wallet

Wallet uses a ledger.

Refunds are idempotent.

### Refund

If payment succeeds but inventory is unavailable, refund processing is asynchronous and delayed.

Do not block a request/thread for one hour.

### Messaging

Important integration events use Transactional Outbox before RabbitMQ publication.

### Redis

Redis is not the source of truth for financial or inventory data.
